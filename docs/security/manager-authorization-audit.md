# Privileged manager tools and authorization audit

Reviewed 2026-11-07 for the container isolation follow-up. This is an evidence report, not an implementation or an approval to execute hostile workloads.

**Result:** PR #18 adds useful placement enforcement but does not enforce the requested boundary against malicious worker/repository content causing privileged agents to act. Role and project scoping authenticate which manager calls a tool; they do not authorize the requested effect on the human's behalf. Existing host tasks, credential assignment, persistent automations, and open REST access remain alternate paths.

## Findings and preconditions

### M1 — High: existing host tasks and host-default projects remain execution deputies

**Precondition:** hostile content reaches a Captain with a local/SSH task or host-default project in scope, or reaches the Coordinator, which can address projects globally. The recipient follows some attacker-chosen instruction. No credential theft or container/kernel escape is needed. A malicious worker can initiate its own Captain turn (`server/tasks.ts:8131-8155`, `server/captains.ts:758-798`); repository text, notices and observations can supply the same influence later.

- `send_to_task` resolves the target by project, checks runner availability, then calls `tasks.send` with arbitrary message/model/routing (`server/mcp.ts:1544-1574`). With no runner change, the new `humanHostPick` and task ceiling do not require new approval. `TaskManager.send` enqueues and schedules (`server/tasks.ts:1359-1363`).
- Alternate host wake paths: Captain `reply_to_agent` (`server/mcp.ts:1679-1683`), `reopen_task` with message (`:1814-1823`), `continue_task` (`:1827-1839`), `retry_task` (`:1842-1845`; `server/tasks.ts:2040-2047`), and queue editing followed by delivery (`server/mcp.ts:1617-1662`). These must share the same execution authorization check. Changing model/harness or pending input on an already-authorized host task can also change what executes.
- `requireNewRunner` accepts host execution whenever the requested/effective runner equals the project's runner (`server/mcp.ts:444-447`). Thus `create_task`/`create_tasks` can start any prompt/model on a host-default project. Creating a task records a new host ceiling from placement, not from an action-specific approval (`server/tasks.ts:1265-1268`). A project runner setting is not approval of arbitrary future work derived from a hostile worker.
- Coordinator `update_settings` can set `runner: "local"`, followed by `create_project` and `create_task`: `server/mcp.ts:2623-2634`, `:881-884`; `server/settingsTools.ts:194-195`. Existing isolated task ceilings survive this, but newly created top-level tasks do not inherit the source worker's isolation.

**Impact:** arbitrary host/SSH agent work under that agent's normal unsandboxed privileges if the recipient follows the injected task. Placement validation answers *where this task may run*, not *who authorized this new instruction*. Preserve the ceiling and add effect authorization at every enqueue/start/steer path, including target tasks already on a host.

### M2 — High: direct agent messaging bypasses even the manager decision

**Precondition:** an isolated worker knows or discovers a local/SSH task's id/title. Source and target are either in the same project or have matching status-only visibility. Recipient interpretation is still required for a particular malicious command, but queuing/waking the host agent is deterministic server behavior.

`deliverAgentMessage` resolves any task id/title (`server/tasks.ts:8084-8085`), checks only the cross-project status-only distinction (`:8092-8105`), queues arbitrary message text (`:8110`), and wakes a resting task (`:8119-8124`). There is no source/target runner trust check or human action grant. `message_parent` calls the same function (`:7267-7269`): an isolated child of a host task must not gain a host instruction channel merely through ancestry. `fyi` suppresses the immediate wake, but stores content for a later read (`:8111-8113`).

**Required enforcement:** isolated task-to-host messages may be inert observations or approval proposals, never executable pending input without a matching human grant. Apply the same rule to subtask reports, parent replies, waits, hooks and manager relays; project membership and matching privacy settings are not execution authority.

### M3 — High: manager identity tools can grant host-held credentials by reference

**Precondition:** a manager is influenced; a useful identity or referenced host login/key exists; the destination runner is compatible. Assignment waits for project tasks to rest. A Captain cannot edit Default/shared identities, but can create identities and assign existing ones to its own project.

- `create_identity`, `import_detected_identity` and `update_identity` take `gh:<login>`, `file:…`, `agent:…` and `gpg:…` references (`server/mcp.ts:2774-2783`, `:2844-2876`, `:2895-2913`). `identity/setup.ts:26-52` reads and stores these values. `identity/detect.ts:801-806`, `:831-842` demonstrate the token/key acquisition path. This review did not invoke it.
- `mayChange` protects shared/default identities from Captain edits (`server/mcp.ts:2725-2729`), but `assign_identity` does not require ownership/approval of the selected identity (`:2952-2954`, `:2741-2753`). `assignChecked` checks compatible runner and resting state (`server/identity/setup.ts:190-198`), not permission to grant those credentials to that project's arbitrary code.
- Removing `runners` restrictions, changing signing requirements, removing a project's own login to fall back to global credentials, or substituting a signing program are sensitive mutations (`server/mcp.ts:2759`, `:2782-2783`, `:2895-2913`). Signing-program validation is an absolute executable-path check, not a human grant (`server/identity/identities.ts:745-751`). Do not treat it as an arbitrary-code-execution demonstration by itself.
- Current limitations matter: file keys must be in the allowed host locations; known SSH login keys cannot be copied into identities permitting remote runners (`server/identity/setup.ts:42-48`). Status-only visibility cannot be loosened through these tools (`server/mcp.ts:2737-2746`). These controls should remain, but do not establish credential delegation authority.

Descriptions saying "after Cody agreed" are not enforced. Encryption and fingerprint-only results prevent direct value disclosure in tool results; they do not prevent unauthorized credential use or forwarding to a later task. All reference resolution, identity assignment and policy relaxation require explicit server authorization of credential scope and destination.

### M4 — High: hooks, schedules and lasting notes can persist or launder the request

**Precondition:** injected content influences a manager that can mutate these resources. Host execution requires a host-default project/existing host target, or a later privileged manager action. Persistence also works in isolated projects without immediate host execution.

- `create_hook(enabled: true)` and `update_hook` directly persist model-selected enabled state, action and prompt (`server/mcp.ts:3103-3138`, `:3194-3211`). The description's human-approval instruction is not checked. A Captain's project hook can use `message_coordinator` (`server/hooks.ts:376-377`), an alternate route to broader authority even though `send_to_captain` is Coordinator-only.
- Hook actions directly call `tasks.requestMerge`, `tasks.sendInput`, manager callbacks, or `tasks.createTask` (`server/hooks.ts:351-384`). In particular, a fresh hook-created task has no subtask ancestry linking it to the source worker's ceiling. A local-default project with an isolated task can therefore create local follow-up work. Rate/loop guards limit repetition, not authority.
- Schedule creation/update accepts arbitrary prompts and enabled state (`server/mcp.ts:2185-2202`, `:2227-2241`). The PR rejects new host overrides on isolated projects, but permits host-default projects; editing/running an existing host schedule is still privileged. `Scheduler.startRun` calls `tasks.createTask` directly and includes the previous run's summary (`server/scheduler.ts:299-318`). Coordinator schedules enqueue a future manager prompt (`:336-347`), not a new human authorization.
- `save_note`, `add_note`, `update_note` and accepting/merging `resolve_suggestion` persist instructions (`server/mcp.ts:1875-1886`, `:1925-1947`, `:1996-1999`). Worker suggestions originate in worker events (`server/tasks.ts:7273-7285`). Notes propagate through `ProjectNotes.changed` (`server/notes.ts:146-150`) and future agent prompts. Manager acceptance must not change worker-origin prose into human authority.

Store the origin of each automation/note and enforce an approved finite policy at **fire/delivery time**, not just when created. Editing any approved prompt/action/filter/runner/credential binding invalidates its approval. Existing automation rows without a grant must not be grandfathered into host authority.

### M5 — High, with direct host-code-execution impact: reachable open REST control plane

**Precondition:** the worker can reach the application with an accepted Host header and no configured password, or possesses the shared operator session/password. Network reachability and credential possession were not tested. This is not a claim that every Docker deployment exposes the API.

- All `/api` routes share `Auth.middleware` (`server/app.ts:986-987`). `Auth.isAuthed` returns true in no-password mode; with authentication, it accepts a signed session or the shared password as a bearer (`server/auth.ts:95-118`). It does not distinguish a human approval from a program possessing that authority.
- `browserBoundary` rejects untrusted browser origins, but deliberately allows origin-less programmatic callers with an accepted Host (`server/browserBoundary.ts:60-97`). Host/Origin checks are useful browser protection, not worker authentication.
- The PR's `/tasks/:id/runner-elevation` requires configured authentication and `confirm: true` (`server/app.ts:1377-1381`). **Other paths remain:** `POST /api/tasks` passes an arbitrary `runsOn` into task creation without the MCP's `requireNewRunner` (`:1365-1369`); `PATCH /api/projects/:id` changes a project's runner (`:1070-1082`); connector/machine/settings routes below expose broader operations. A new top-level task can acquire host placement without calling elevation.
- Concrete native execution sink: connector create accepts a command and argument list (`server/connectors/connectors.ts:135-151`); `POST /api/connectors/:id/test` runs it through `StdioClientTransport` on this computer (`server/app.ts:1219-1220`, `server/connectors/service.ts:102-113`, `server/connectors/probe.ts:54-56`). It need not be a working MCP server for its process to start. Environment reduction does not sandbox filesystem/process access. Commands such as an explicitly configured package runner can also install dependencies as their own side effect; there is no separate manager `install` tool.

An isolated worker must receive neither operator credentials nor network authority over this API. Fail closed for sensitive REST actions when human authentication is disabled; retain a usable open-mode read-only/proposal workflow or require an explicit operator setup step. Do not exempt task creation, integration testing, machine probes, or settings as "already trusted" while protecting only elevation.

### M6 — Medium alone; compounds M1–M4: phase and later-turn trust are not enforced

- Manager MCP bearer tokens encode only role/project/readOnly. `callerFor` and `mcpHandler` build a fresh server per request with no active turn, input origin, phase or approved action binding (`server/mcp.ts:3566-3600`). The Coordinator gets all its tools; Captain tokens are random and project-scoped (`server/app.ts:698-704`, `server/captains.ts:312-329`). These are real caller controls, not action authorization.
- Claude managers omit shell/edit built-ins and use `dontAsk`; outside normal turns the launch omits allow rules (`server/chatAgent.ts:21-28`, `server/orchestrator.ts:880-906`, `server/captains.ts:1428-1454`). This is useful defense in depth, conditional on the installed CLI honoring those rules.
- Codex managers use read-only sandbox, ignore user config/rules, disable shell/exec/subagent features, and set approvals to never (`server/codex.ts:125-155`). They still auto-approve Box Yard MCP tools (`:146-149`). Summary passes (`server/orchestrator.ts:515`, `server/captains.ts:1377`) pass the **same** manager MCP token through Codex launch (`server/orchestrator.ts:934-943`, `server/captains.ts:1491-1500`); no read-only phase is passed. A summary pass is therefore not server-restricted to observations.
- Captain turns combine worker messages, notices and human messages (`server/captains.ts:1014-1053`). Runner picks are turn-wide (`server/mcp.ts:428-447`) and forwarded from Coordinator to Captain (`server/captains.ts:348-354`). A human `@local` pick is stronger than model `runs_on` alone, but authorizes neither a particular target nor particular instructions. SSH approval is a runner category; machine label/default mapping may select a different machine later.
- Read-only observation can poison a later human turn: task replies/errors/titles, repository text, artifacts, note suggestions, FYI messages, external search/MCP descriptions and saved compactions are data controlled or influenced by untrusted parties. Sessions resume and compactions are replayed (`server/orchestrator.ts:799-827`). A later human saying "status?" or choosing a runner cannot cleanse that prior context. Marking only the *current wake trigger* as human does not solve this.

**External integrations bypass a Box Yard-only tool gate.** `list_connectors` is read-only and connector add/edit/scope/sign-in are intentionally absent from manager MCP (`server/mcp.ts:2645-2692`). Stdio commands run under reduced env, **not an OS sandbox** (`:44-60`); HTTP connectors have the authority of their configured credentials. If a configured connector exposes host shell/files/control-plane access, worker-influenced managers can use it directly. Even nominally read-only connectors return untrusted tool descriptions/data. Codex managers currently receive only Box Yard MCP through `codexChatLaunch`; they do not receive these Claude session connectors. Side threads do not receive connectors. Do not regress those narrower paths.

## Minimal maintainable implementation strategy

1. **One explicit effect catalog, default deny.** Extend the server's registration helper (existing read-only wrapper is a precedent) so every tool declares its effect resolver: observation, managed-storage write, isolated task dispatch, host dispatch, sensitive configuration/credential grant, or persistent automation. Unknown/new tools refuse mutation until classified. Preserve project/status-only checks as an additional boundary. A catalog test must cover all 82 names, plus new names, instead of a second manually maintained denylist. Enforce actual effects in `TaskManager`, identity/settings/machine/integration services too; an MCP-only wrapper misses REST, hooks, scheduler and worker callbacks.
2. **Authenticated actor is distinct from authorized effect.** Derive an immutable `ActionContext` from the server's token/session/worker polling context: principal, project/task, active turn/phase, observation provenance and narrow server-held grants. No request field named `approved`, `from_human`, reason text, model classification, claimed approval, or forwarded message can create a grant. Fail closed for missing context. Use distinct server-created observation-only credentials for summaries/compactions, side threads and background planning; bind normal manager tokens to a live phase/turn and revoke on completion.
3. **Managers propose sensitive actions; the UI approves the stored action.** Human approval must show the exact operation and target task/project/machine, full new or edited instructions/queue versions, runner plus actual machine identity/host-key binding, harness/model, repository revision/workspace/archive and attachment digests, environment/credential **references and scope** (never raw secrets), affected resources/spend bounds, automation trigger/filter/prompt and duration/count. Execute the canonical immutable payload stored by the server, not model arguments supplied after approval. Make approvals single-use, expiring and atomically consumed; invalidate on any relevant target/input/config change. For multi-step automation, approve a finite explicit policy with scopes/budgets and revalidate every effect. Approval of a runner category alone is insufficient.
4. **Constrain every delegation path.** Worker-origin messages/results/repository content remain observations across Captain/Coordinator relays, direct task messages, subtask reports, hook interpolation, schedules, note promotion, artifacts, compactions and retries. Automatic dispatch can remain within an explicitly granted isolated trust domain and credential budget. Sending/steering/resuming any existing local/SSH task, changing its pending instructions/model, or creating a new host task needs the matching grant. Validate again before placement/launch and when queued messages are delivered; never infer authority solely from the target's host ceiling. Do not let "same project" or "parent task" widen it.
5. **Broker privileged connector calls.** A raw external MCP namespace bypasses server policy. Keep potentially privileged native connectors off managers, or proxy them through the same effect/approval service with per-tool scopes; sandbox their processes and narrowly scope credentials. Treat connector installation, command testing/startup, OAuth completion callbacks and secret/scope changes as sensitive effects. MCP tool annotations or descriptions are not trusted effect declarations.
6. **Close the programmatic REST alternate path.** Protect all listed sensitive route families, including task creation and probes, with server-derived human approval. Require configured authentication for privilege grants; do not grant open-mode programmatic callers human status. Workers must not hold operator password/cookies/manager bearers; supplement application auth with an enforced container-to-host/LAN control-plane network policy. One shared operator login can remain: this is capability separation between code/model execution and operator approval, not per-user isolation.

**Compatibility and limits:** retain human-selected local/SSH workflows through explicit approvals and saved finite automation grants, and preserve current project/status-only scoping, no-fallback placement, archive/work-preservation checks and task ceilings. Do not auto-approve legacy host tasks, schedules, hooks, notes, identities or integrations merely because they already exist. Offer clear proposals/approval requests instead of silently dropping work; allow harmless measurements/managed artifact writes under bounded policies. A "human turn" toggle would preserve convenience but fail the stated threat model because persistent sessions and later observations remain influenced.

Even exact platform dispatch approval does not make an unsandboxed local task safe if that task's model already has arbitrary shell access and reads attacker-controlled repositories/reports. For that stronger guarantee, run such work in an enforceable sandbox or mediate its host commands/files/credentials through a narrow execution broker. Server dispatch authorization closes these deputy paths; it is not an absolute no-escape promise for arbitrary host code or the installed runtime.

## Focused verification for the implementation owner

Use mocked providers/in-memory dispatch, never live host work: isolated worker → same-project and other-project local/SSH message; isolated child → host parent; malicious read result → later human status turn; mixed worker/human turn with `@local`; runner alias/machine-label changes; create/batch/send/reply/reopen/continue/retry/queue edit/deliver; enabled hook plus merge callback; previous schedule summary and mutable legacy schedule; note accept/merge; identity assign/import/reference/remove-login/runners relaxation; Codex and Claude summary phases; scoped external connector calls; open-mode task creation and connector-test denial. Assert denial **before** enqueue, process start, provider call, file/secret read, credential grant or settings mutation, including transitive observation callbacks. Positive tests should consume exactly the approved canonical action and reject replay, changed payload/target and stale approval.

## Implementation compatibility addendum: permanent manager restrictions

The parent's proposed simpler boundary is preferable to a per-turn taint exception: **manager tokens permanently lack host-dispatch and sensitive-control-plane capabilities, including on later human turns.** Human UI/API operations use a different authenticated server principal. Model arguments, a human-looking input source, a saved runner pick, or another manager's relay never upgrade a manager token. This avoids trying to cleanse a persistent model session after reading worker content. It still requires the alternate-path restrictions below; an MCP name allowlist alone is insufficient.

### Built-in file tools and HTTP compatibility

**Current Claude flags are narrower than blanket Read/Grep/Glob access.** `CHAT_ALLOWED_TOOLS` contains WebSearch/WebFetch/ToolSearch, not unqualified Read (`server/chatAgent.ts:21-28`). Coordinator Read rules cover compactions and uploads (`server/orchestrator.ts:923-926`); Captain rules additionally cover its clone (`server/captains.ts:1466-1467`). `--tools` makes Grep/Glob available to Captains, but the allowed-path behavior still depends on the installed Claude CLI's permissions. This audit has not demonstrated arbitrary-file access or a symlink escape in that CLI. The code contains no Box Yard server-side realpath/no-symlink enforcement for those built-ins.

For a small enforceable boundary, remove manager built-in file tools and `repo_clone`, and provide bounded server-mediated content reads by authorized artifact/upload/history/repo-snapshot identifiers. Preserve sealed-project checks. Snapshot reads must reject symlinks and special files, stay inside an immutable approved root, and bound traversal/bytes; a lexical prefix alone is insufficient. Raw access to the shared uploads directory also cannot enforce per-project attachment visibility. Compatibility cost: Claude Captains lose on-demand code browsing until this reader exists; Codex managers already omit file tools (`server/chatAgent.ts:153-158`). Existing clone Git disables hooks and skips LFS downloads (`server/captainRepo.ts:297-314`), but clone/fetch/reset/clean and credential use remain host effects, so this is a conservative removal rather than a demonstrated clone execution exploit.

Remove all external manager connector configuration and namespaces, including resume/side-thread/summary launch paths; merely omitting names from one CLI allowlist does not revoke a live token or external session. Claude currently grants whole connector namespaces; Codex currently has no external manager connectors. Keep Box Yard ToolSearch only for the restricted catalog.

WebFetch is **not** a general arbitrary-POST tool, so do not claim it directly submits arbitrary connector configuration. It can read reachable open APIs/GET endpoints and disclose already-read content via URLs. Enforce private/loopback/control-plane destination restrictions in a broker or remove manager WebFetch; labels in prompts are insufficient. External search/results remain untrusted but cannot create privileged authority under the permanent policy.

Open-mode `Auth.isAuthed` returns true (`server/auth.ts:95-99`); therefore a generic `isAuthed` check does not establish a human principal. Sensitive UI/API routes must require configured authentication, not only the existing middleware, and worker isolation must prevent access to operator credentials. Host/Origin checking deliberately permits origin-less programs (`server/browserBoundary.ts:60-97`) and does not prove human intent. Cover native connector test/startup, project/task runner/default creation, identity references, machine probes, Docker/image configuration and all automation writes; protect GET routes that perform sensitive work too. A local/private API that remains open to workers bypasses the entire manager policy.

### Non-manager bypasses that must close simultaneously

- **`list_agents` makes host targets discoverable.** `TaskManager.directory` includes every non-done task (`server/tasks.ts:9384-9389`); it is published to shared Redis (`:9392-9399`) and included in turn startup (`:6076`, `:6141`). Runner `liveDirectory` reads Redis or `turn.json` (`runner/box-runner.mjs:2057-2066`), and `list_agents` returns ids/titles/projects (`:2088-2091`). Filtering the directory to permitted peers reduces disclosure, but ids/titles are not secrets or authorization. Keep server-side checks in `deliverAgentMessage` even when a target id is guessed, copied from repository text, or learned earlier.
- **Direct messages and automatic reports bypass manager MCP.** `message_agent` emits a worker event (`runner/box-runner.mjs:2093-2097`) consumed by `TaskManager.apply` (`server/tasks.ts:7233-7234`). `message_parent` uses that delivery (`:7267-7269`), but `reportToParent` separately queues arbitrary report text, marks a resting parent queued and schedules it (`:7955-7973`). An isolated child must not feed an unrestricted host parent's live context, even if it does not wake a new turn. Enforce this at both queue/wake paths and at `subtasks.json` report delivery (`:8037-8050`) to an already-running parent's `wait_for_subtasks`. Host parents spawning contained children must receive inert human-reviewable reports, or themselves operate under an enforced sandbox/broker. `fyi` prevents immediate queue/wake only; it does not make later unrestricted host-model ingestion safe.
- **Legacy hooks and schedules survive manager mutation denial.** Hook sinks directly call merge/send/create/manager callbacks (`server/hooks.ts:351-384`); schedule sinks create tasks or enqueue Coordinator prompts (`server/scheduler.ts:299-347`). Worker finished/PR-ready/failed events, summary variables and previous schedule replies remain attacker-influenced inputs. A previously human-enabled hook is not approval of arbitrary future interpolated host instructions. Disable host-producing automation without an approved finite policy, and apply the same contained-only sink checks to all fires. QStash signatures and OAuth state authenticate callbacks, not broad privileged effects.
- **Read callbacks still fire legacy automation unless removed or constrained.** PR refresh in read tools reaches `prChanged`, `followUpMerge`, issue closure/archive and event hooks (`server/tasks.ts:7376-7411`). Removing refresh from manager reads does not close the independent background poll. Enforce effect limits at downstream sinks too.
- **Human route/host session contamination is a separate limit.** Keep reports, notes, compactions and prior observations untrusted across turns. A human status message or generic Continue click must not allow a manager to resume unrestricted host work. If the human explicitly starts a host task, approval must cover the full canonical instructions, target session and its existing queued/history inputs, placement/workspace/repo/archive/attachments and credential scope; existing poisoned host sessions cannot be treated as clean. Even a fresh exact dispatch approval cannot make arbitrary unsandboxed host code safe when it subsequently reads malicious repository content. That stronger requirement needs host task sandboxing or a narrow execution broker.

Implement the permanent catalog gate once, then centralize the contained-only dispatch check in task enqueue/steer/model/launch services and thread immutable principals through callbacks. Maintain an exhaustive registration-policy test, no privileged manager exception for human-origin turns, and mocked tests for directory target guessing, automatic reports, live waits, FYI replay, legacy hooks, background PR callbacks, open REST and every harness phase. This is substantially smaller and easier to audit than maintaining mutable per-turn approval taint, while deliberately moving host orchestration/settings/notes/automation operations to authenticated human workflows.
