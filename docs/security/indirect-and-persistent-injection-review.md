# Indirect and persistent prompt injection review

Scope 3 of the container runner isolation audit. Reviewed the public repository and **PR #18 at `ed152eaf5271ba84782003afe753a94ea1f4e24c`**, fetched into a detached checkout inside this task's workspace. GitHub reported the PR OPEN at inspection. All source locations below refer to that commit, not this report branch's older base.

Reference: [reviewed source](https://github.com/AgentSystemLabs/box-yard/tree/ed152eaf5271ba84782003afe753a94ea1f4e24c). Static review and eight harmless offline data-flow checks only. No live model attack, server traffic, credential reads, Docker operation, installation, production edit, push, PR or merge was performed. This report does **not** establish arbitrary host code execution by a tested model; it establishes delivery/authorization paths that permit an injected recipient model to request such work.

## Assessment

**High residual risk.** PR #18 constrains a task's physical placement and explicit descendants. It does not constrain the authority of work caused by that task's messages, reports, stored content, or a later decision after an authorized read. An existing host task, a new top-level task, or a privileged manager can become a deputy without the originating worker changing runner or possessing a stolen token. These routes require no Docker escape.

The PR's disclosure of message-relay risk is accurate (`docs/security/runner-remediation.md:117`). Its claim that descendants remain contained is materially narrower than causal containment: hooks, new tasks, manager relays and later sessions can lose the original execution restriction. Human-selected project defaults and turn-wide runner picks are broad grants, not approval of each resulting action.

## Findings

### 1. High — worker messages can wake existing host tasks across project boundaries

**Evidence.** `server/tasks.ts:8064` (`deliverAgentMessage`) resolves a target from the global task table by id or title at `8084`. Its cross-project check at `8092` rejects only projects with *different* status-only flags. At `8110` it queues attacker text as `agent:<id>`; at `8119` it queues a resting target for execution and schedules it. It does not inspect either task's runner ceiling, physical runner, identity execution rights, or a human approval. `message_parent` takes the same path (`7267`).

The directory is global (`server/tasks.ts:9384`); workers receive it in prompts (`server/prompts.ts:251`) and `list_agents` (`runner/box-runner.mjs:2057`, `2088`). Removing Redis from new worker config (`server/tasks.ts:6630`) does not remove these file-event message paths (`runner/box-runner.mjs:2097`, server event dispatch `server/tasks.ts:7233`).

**Preconditions and path.** An isolated malicious worker has a known target task id/title. A local/SSH task already exists, can run, and shares the source's status-only flag (same-project delivery also works). Sending a plausible request causes its next turn. The target must then follow the malicious content for malicious shell work to occur; delivery and wake do not depend on that persuasion. A benign intermediate isolated worker can relay the request to the host target, defeating any fix that checks only the immediate sender's placement or wording.

**Gap and fix.** Runner ceilings authorize *where a target may run*, not *who may supply executable work to it*. Default worker-to-worker traffic to data-only delivery; require an explicit source→target execution capability to wake or steer a target with greater/different authority. Apply it to parent reports, waiting-agent replies, queued edits, retries and mid-turn delivery. Scope across projects independently of the privacy flag. Rate limits and labels do not supply this authorization.

### 2. High — privileged relays and global defaults manufacture fresh host authority

**Evidence.** A worker's `message_captain` is stored as a user-role message with agent metadata (`server/captains.ts:758`, `779`), labelled when rendered (`1018`), and passed to a persistent Captain with privileged MCP tools. Tool `send_to_task` uses the **caller's** source (`server/mcp.ts:424`, `1566`); it carries no original message/read dependency. Omitting `runs_on` leaves an existing host target's placement intact. Captain replies to Coordinator requests (`server/captains.ts:1093`) and automatic reports (`1129`) become Coordinator notices (`server/app.ts:808`), or tool results through `ask_captain` (`server/captains.ts:371`). Neither includes a transitive authorization ceiling.

The Coordinator can `send_to_captain` for any project (`server/mcp.ts:814`) and message any scoped task; the Captain's own project checks (`319`, `327`) do not survive a Coordinator relay as a causal constraint. A Coordinator automatic wake explicitly permits starting a clear next step of prior work (`server/orchestrator.ts:719`).

There is also a concrete default-setting chain: `update_settings` calls `settingsTools.update` without an action approval (`server/mcp.ts:2632`); `runner` is writable (`server/settingsTools.ts:195`, `330`). `create_project` inherits that default (`server/mcp.ts:884`, application injection `server/app.ts:919`). A host-default project's new task passes `requireNewRunner` (`server/mcp.ts:444`) and receives a local/SSH ceiling at creation (`server/tasks.ts:1266`). The prose instruction to confirm runner changes (`server/prompts.ts:466`) has no server approval object. The chain requires host execution to be available and allowed by applicable identity limits; it does not require an existing host task or a human runner pick.

**Preconditions and path.** An injected Captain relays an urgent-looking blocker/report while the Coordinator asks about that project or reads its updates; the Coordinator sends the supplied work to a host task/project, or changes defaults and creates a new project/task. These are model-decision-dependent chains. No direct Captain out-of-scope MCP call is asserted. Status-only filtering limits disclosure, but its allowed titles/state/PR strings and allowed Captain replies remain injection surfaces.

**Gap and fix.** Authorize the requested effect, not the manager's identity or latest sender. Host dispatch, host defaults, schedule/hook activation, repository/identity changes and delegation need separate server capabilities. A manager must not grant itself or its descendants host authority through settings, project creation or a rewritten relay.

### 3. High — mixed inputs broaden human runner selection to unrelated injected actions

**Evidence.** `shared/runTargets.ts:279` collects all picks and drops messages without one; a single agreeing pick wins for the entire batch. Captain prompts concatenate multiple messages plus unseen notices (`server/captains.ts:1018`, `1035`, `1043`) and derive one `turnPicks` value from the batch (`1053`). Coordinator turns combine notices and human requests similarly (`server/orchestrator.ts:748`, `759`). MCP `picked` overrides every task create/send in that turn (`server/mcp.ts:434`); `humanHostPick` checks only authentication-enabled and matching runner (`439`), and can elevate a task at `1560`. The selected pick also travels to any Captain the Coordinator messages (`server/captains.ts:348`).

**Preconditions and path.** Authentication is enabled and a real human selects `@local`/an SSH target for legitimate work. A worker message/notice is processed in that batch, or its instructions already exist in session memory from an earlier report/repository read. The model acts on the injected work while the broad pick is active. The human selected a runner; the server cannot establish that they authorized the injected target, prompt or effect. The worker cannot forge pick metadata merely by writing `@local` in its message; this finding does not rely on that.

**Gap and fix.** Replace turn-wide ambient elevation with a server-held grant bound to the exact human-approved task/action and effect. Bind project/task, runner and machine identity, repository/head where applicable, operation, argument/content digest, expiry and use count. Unrelated requests in the batch, stale queued messages and relays must not borrow it. Apply the same checks even on a later human-triggered turn: a new human message does not erase prior untrusted context.

### 4. High — stored summaries and model-curated notes persist instructions and cross task ceilings

**Notes path.** A worker supplies `suggest_note` content and reason (`runner/box-runner.mjs:2108`; server storage `server/tasks.ts:7273`). The default-enabled notes retro includes worker summary, suggestion and reason (`server/retro.ts:87`) and instructs the Captain to resolve them without human review (`111`). `notes.resolve` creates or rewrites a lasting note based on the model decision (`server/notes.ts:104`, `113`, `116`), with no executable-policy approval. Notes are injected as “lasting rules from Cody and the project's Captain” into future task prompts (`server/prompts.ts:244`) and Captain state (`server/captains.ts:1207`, `1229`). A worker can try to replace a valid rule by a merge as well as add a new one. Acceptance is model-dependent; workers do not directly write approved notes.

**Reports/automation path.** Worker `finish` and result text become the stored summary (`server/tasks.ts:7351`, `7481`, `7494`) and notices (`7530`). Child reports are queued to parents and saved in KV (`7955`); `reportText` embeds them directly (`server/subtasks.ts:86`). Tool reads and related-task context include these summaries (`server/handoff.ts:138`; `server/mcp.ts:405`). Hook substitution preserves worker summary/title/branch strings (`shared/hooks.ts:188`, `210`); hooks dispatch them to Captain/Coordinator or a task (`server/hooks.ts:365`).

**A specific ceiling discontinuity:** `create_task` hooks create a top-level task with project id, rendered prompt and hook source only (`server/hooks.ts:381`). TaskManager checks source containment only for `input.subtask` (`server/tasks.ts:1240`), then grants a fresh top-level ceiling from the project default (`1266`). An isolated task in a local/SSH-default project, plus an existing enabled create-task hook using its summary/title, can therefore feed instructions into a **new host task**, despite its own isolated ceiling. This does not require persuading a manager to change runner. It still requires the new host model to obey the malicious content. Similarly, a schedule's next run incorporates its predecessor's full summary (`server/scheduler.ts:299`) and creates a new task at the saved/project runner (`313`). A future host run after an authorized runner/default change can consume that stored content.

**Other persistence.** Normal session resume retains model context. Missing-session recaps strip message metadata down to role+text (`server/captains.ts:1278`; Coordinator `server/orchestrator.ts:820`). Worker recap and cross-harness handoff do likewise (`server/prompts.ts:368`). Summaries survive compaction and seed fresh sessions (`server/captains.ts:1377`, `1407`, `1258`). A clean last-turn sender is therefore insufficient. Titles and PR/branch metadata remain content even in status views; limits/Markdown quoting reduce volume, not authority.

**Preconditions and fix.** Notes attack: retro enabled, model accepts malicious rule, and a later privileged agent consumes it. Hook attack: an enabled matching hook interpolates attacker-controlled fields and the destination has host rights. Schedule attack: later run has greater authority than the stored source, or relays to it. Preserve origin and execution ceilings across suggestions, accepted/merged notes, summaries, notices, templates, hook/schedule runs, recaps and related-work links. Treat notes as advisory data; only an independent human action can change execution policy. Pin automation grants and enforce them at **fire time**, including changing project defaults and previous-run sources. Existing automation approval is not approval of arbitrary future interpolated worker instructions.

### 5. Medium, High when a privileged deputy follows it — read-only side-thread routing launders context

**Evidence.** Side-thread MCP mutation is genuinely server-refused (`server/mcp.ts:262`; allowlist `server/sideThreads.ts:70`). Ordinary ask/task threads have no automatic work dispatch. However **reply threads** interpret model `[[route:agent]]` / `[[route:chat]]` directives (`server/sideThreads.ts:263`, `669`). `forward` sends human words to a task or quotes up to 280 characters of the original message into the main chat (`697`, `299`). Application routing labels the result as `cody` (`server/app.ts:751`, `762`). The router sees original worker-derived notices and forked/summary context (`server/sideThreads.ts:638`).

**Preconditions and limit.** A real human opens/replies to a thread anchored to attacker-influenced content. Injection may alter routing, including an informational question being forwarded to a privileged main chat, or placing the attacker-controlled excerpt beside an ambiguous “do it” reply. It cannot insert arbitrary fresh text into `toAgent`, which forwards the human's words unchanged. The direct route targets only the anchor's task; no arbitrary task-id override was found in this path. There is no autonomous worker-only side-thread breakout established.

**Fix.** Routing is an authorization-sensitive operation despite the thread's MCP read-only status. Preserve the quote's original origin, distinguish actual human text from referenced content, and require explicit routing/effect approval when the destination has broader execution rights. An instruction to answer a question must not itself authorize execution.

## Recommended enforcement model

1. **Make every action server-authorized.** Keep UI-authenticated human principals separate from manager/worker principals. Use server-issued capabilities for concrete effects, per project/task and actual runner/machine. `source`, `trigger`, a model-supplied reason, text claiming approval, and a manager's own decision are not approval. Record grants/denials for audit and check again at dispatch, launch and automation fire.
2. **Separate data delivery from executable work.** A worker report may enter a scoped inbox or data lookup without granting the reader permission to act outside its existing narrow operation. Crossing to host execution, another project's operations or more powerful credentials requires a valid effect grant, including for existing tasks and mid-turn steering. Do not treat a reused local task as a preapproved general-purpose executor.
3. **Preserve causal provenance, but do not depend on model taint judgement.** Store immutable origin ids, dependency references and capability ceilings for original messages, files, repository revisions, tool output and derived records. Relays/rewrites/merges must not improve authority. Keep provenance across queue mixing, retries, compaction, archive/recap and harness changes. Server-mediated reads should register the read dependency; raw file/web reads require treating the entire continuing session as exposed to untrusted content. Do not clear that state because the next prompt came from a human. A tool argument claiming its own lineage cannot be trusted.
4. **Use narrow host operations or keep execution isolated.** An arbitrary host shell with access to mutable repositories, ambient logins and unrestricted tools cannot reliably execute only the semantic intent in an approved natural-language prompt. Prefer brokered fixed host operations with validated arguments, bounded workspace/file/network access and separately scoped credentials. Keep general model work isolated, even when the model believes a host command is harmless. Bind approval to concrete reviewable effects; execution of mutable repo scripts must invalidate a grant when inputs change.
5. **Protect persistent policy and automation.** Human-reviewed grants must cover host defaults/elevations, executable note/policy changes and enabled schedules/hooks. Automatic notes curation can remain for non-authoritative facts. Hooks/schedules should have fixed scoped capabilities, independent of future project defaults; interpolated outputs remain data. Reject or request a concrete approval when a cause has less authority than the requested effect. No model should mint capabilities by creating projects, schedules, notes or new tasks.

The policy must cover direct task APIs, manager MCP, file-event worker tools, `message_agent`/`message_parent`, subtask reports, Captain waits/replies, finish/results, queue edits/steering, schedule/manual/catch-up runs, hooks, retries/resume, related tasks, artifact/PR/repository reads and reply-thread routing. Future routes must default to denial until assigned an operation policy.

## Compatibility and limits

- Captain scope checks and status-only guards are useful confidentiality boundaries; they are not execution-trust checks. Two sealed projects currently can message each other just as two open ones can. Cross-project capabilities must be explicit and cannot be inferred from matching visibility.
- Host tasks remain supported through narrow human grants. Unrestricted autonomous messages to existing host tasks, broad turn-wide `@local`, automatic host follow-ups from worker summaries, and model-only approval of policy changes would require redesign or deliberate opt-in. Strict task-bound grants reduce hands-off workflows; structured host operations preserve more automation than prompt-based approval.
- Claude managers expose read/search tools and MCP, not Bash/Edit (`server/chatAgent.ts:21`, `26`; Captain launch `server/captains.ts:1428`). Codex managers request a read-only sandbox with shell/multi-agent features disabled (`server/codex.ts:128`, `133`, `155`), but retain approving MCP calls (`147`). These configurations were reviewed, not runtime-verified. The reported chains need neither manager shell access nor a failure of those flags.
- Claude, Codex and Cursor tasks share the event/tool dispatch in `runner/box-runner.mjs` and `server/tasks.ts`; a malicious harness can emit its allowed events directly. Enforce policy centrally, not with harness wording or a runner-side refusal. Preserve the same policy through CLI/SDK and cross-harness continuation. Codex managers lack Captain repository file tools, but still encounter worker/tool/recap content; Claude adds direct repository reads (`server/captainRepo.ts:4`, `server/captains.ts:1466`). Repository read-only status prevents edits, not instruction influence.
- Labels, JSON/Markdown quoting, prompt warnings, content filters and one-turn taint can help model behavior, but cannot establish the requested boundary. Human approval itself can be socially manipulated; the UI must show concrete effect and provenance, not approve a model's claim that approval was already given. Once a human deliberately grants arbitrary host execution, residual model/repository risk remains. This is not a no-escape guarantee.
- Network/daemon isolation, shared-worker spoofing, credential reach and archive parsing are sibling audit scopes. This report assumes ordinary allowed event paths and no token theft; it does not establish those independent boundaries as safe. External connector mutation capabilities also need the same action policy and were not exhaustively audited here.

## Offline validation and implementation acceptance cases

Run [indirect-injection-offline.mjs](indirect-injection-offline.mjs) with Node 24+ and a checkout of the reviewed commit: `node docs/security/indirect-injection-offline.mjs <checkout>`. It uses native TypeScript stripping, resolves imports only inside that checkout, installs nothing and calls no server/model. Result: **8 checks passed**. It verifies current helper behavior for mixed runner picks, mixed notification trigger, raw hook/child-report text, recap/harness-handoff metadata loss and notes entering task context. These are observations of current unsafe composition, not regression assertions of a desired security fix. Production typecheck/build/test gates were not run: dependencies are absent and this audit changes documentation/fixture only.

Parent implementation should add server tests for:

- Box/Docker/remote worker → same-project and cross-project existing local/SSH task, including via another worker and FYI later read.
- Worker → Captain → Coordinator → another project/host task; repeat after a genuine read-only human question, then a later unrelated human action.
- Genuine `@local` for task A batched with worker message B; B must not create/elevate/steer any host task. Repeat after Coordinator→Captain forwarding and retry.
- Isolated task in a host-default project → existing create-task hook using `{summary}`; reject host execution without a matching grant. Repeat after a default changes and during catch-up.
- Malicious suggestion accepted/merged, auto-retro disabled/enabled, fresh task, missing session, compaction, archive restore and Claude↔Codex↔Cursor continuation; no content record may become execution approval.
- Stored previous-run summary into a later host schedule; model-created/enabled hook or Coordinator schedule; model setting `runner=local` then creating a project.
- Reply-thread question on a worker-derived notice that emits a route directive; MCP refusal must not be the only check on the router's effect.
- Positive cases: exact human-approved host operation and ordinary isolated collaboration continue to work; changed payload/head/target, replayed grant and transitive privilege widening fail closed.
