# Subtask environment inheritance

Every task-spawned descendant stays in the original task's physical environment type. Docker descendants use Docker containers; Upstash descendants use Upstash boxes. New instances of the same type are allowed. Local tasks stay local, SSH tasks stay on SSH machines, and RunPod, Vast.ai and Daytona each have their own type. SSH machine identity, user identity and GPU model do not define new types.

The server records the original physical provider before the first launch. Descendants inherit an immutable SQLite `tasks.environment_type` value. Runner requests, worker event fields, identity allowlists, manager tools and project defaults cannot replace it. A broad `gpu` or `box` runner choice does not authorize a different physical provider: the automatic box provider's local folders are local, not Upstash.

`same` shares the parent's slot only when its current placement has the inherited type. If the parent later moves, its existing descendants can use another instance of their original type. Omitted/null selections pin to that type rather than following future project defaults. GPU descendants also pin the original cloud. Explicit conflicting selections fail with a `Subtask environment restriction` error. Placement checks apply again to the actual target before assignment, scheduling, restore and launch; an unavailable type waits without falling back to another provider.

Top-level task creation and runner changes remain available. The original descendant type does not change when a top-level task moves: it can spawn again only while physically placed in its original type. Existing descendants keep their restriction through retries, archive/recap recovery, box replacement and server restarts. A restart requests the stop of an incompatible existing descendant turn instead of reattaching it; an unreachable provider may prevent that stop from completing.

## Existing stores

The append-only migration adds the nullable type column and a trigger preventing changes once populated. It deliberately does not backfill from requested runners, project defaults or worker files. On first use, an existing lineage is checked through its parent links, project, root and depth. The root's first recorded turn must have an authoritative placement and provider record (stable own-runner IDs can use their server provider routing). A fresh task with no prior turn can use its current server placement. Verified descendants are then pinned.

Missing original turn placement/provider records, missing ancestors, cross-project links, cycles or conflicting persisted types block descendant creation/placement with a clear error. Ambiguous legacy top-level tasks may continue their own work, but cannot spawn until authoritative original lineage exists; changing a runner or retrying does not erase this restriction. Starting a new top-level task intentionally selects a new origin. This conservative compatibility behavior can leave old trees waiting for review.

This boundary governs server-orchestrated task placement. It does not undo past execution, harden containers, restrict a task's network/process capabilities inside its environment, or authorize an agent to control manager tools. Mock mode's folder providers simulate runner types for development and tests; they provide no physical isolation. Regression fixtures use inert provider routing and do not execute live agents or contact providers.
