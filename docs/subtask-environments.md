# Subtask environment inheritance

Every task-spawned descendant stays in the original task's physical environment type. Docker descendants use Docker containers; Upstash descendants use Upstash boxes; Daytona descendants use Daytona sandboxes. New instances of the same type are allowed. Local tasks stay local and SSH tasks stay on SSH machines. SSH machine identity, user identity and GPU model do not define new types.

RunPod and Vast.ai GPU boxes cannot spawn subtasks, including `same`, omitted/null runner choices, explicit runner requests and nested descendants. The server rejects worker events and direct manager creation with `Subtasks are not supported on RunPod GPU boxes.` or the corresponding Vast.ai message. The agent's system prompt and tool guidance tell it to explain this limitation when asked to use sub-agents and do the work itself. This decision does not disable intentional top-level RunPod/Vast.ai tasks. Existing compatible descendants may continue in their original type, but cannot create another generation. RunPod, Vast.ai and Daytona remain distinct physical types for lineage and placement checks.

The server records the original physical provider before the first launch. Descendants inherit an immutable SQLite `tasks.environment_type` value. Runner requests, worker event fields, identity allowlists, manager tools and project defaults cannot replace it. A broad `gpu` or `box` runner choice does not authorize a different physical provider: the automatic box provider's local folders are local, not Upstash.

`same` shares the parent's slot only when its current placement has the inherited type, and never on this computer: there every turn, at any depth, takes a Settings › Local agents slot of its own, and a parent waiting in `wait_for_subtasks` lends its slot to its sub-tasks until its wait is over (see [One turn cap on this computer](#one-turn-cap-on-this-computer)). If the parent later moves, its existing descendants can use another instance of their original type. Omitted/null selections pin to that type rather than following future project defaults. GPU descendants also pin the original cloud. Explicit conflicting selections fail with a `Subtask environment restriction` error. Placement checks apply again to the actual target before assignment, scheduling, restore and launch; an unavailable type waits without falling back to another provider.

Top-level task creation and runner changes remain available. The original descendant type does not change when a top-level task moves: it can spawn again only while physically placed in its original type. Existing descendants keep their restriction through retries, archive/recap recovery, box replacement and server restarts. A restart requests the stop of an incompatible existing descendant turn instead of reattaching it; an unreachable provider may prevent that stop from completing.

## One turn cap on this computer

Settings › Local agents (`localAgents`) bounds every task turn on this computer: top-level tasks, sub-tasks at any depth (`same` included), resumed and follow-up turns, and turns that hooks, schedules or a Captain's `send_to_task` start. All of them take a slot through the one scheduler pass (`schedulePass` → `place` → `Store.claimTurnSlot`). Turns that can't get a slot stay queued, high priority first, then first in, first out (`shared/priority.ts`). Their wait reason names the tasks holding the slots.

A turn that waits for its sub-tasks in `wait_for_subtasks` lends them its slot. The runner reports the wait (`subtask_wait`), and the server stops counting the turn (`TaskManager.parkForSubtasks`, `tasks.parked_turn_id`). When the wait is over, the runner asks for a slot back (`subtask_wait_end`). The turn waits in the same queue, ordered by when it started, until the server grants a slot (`slot-<id>.json`). The tool answers only after that. So 20 sub-tasks under a cap of 3 never wait on the parents that started them. A parked turn's agent process stays up, idle, while it waits. A parent that ends its turn instead holds no slot until its sub-tasks' reports start its next turn.

New turns here also wait while this computer's memory is past Settings › Memory and load (`memoryMaxUsedPercent`, `memoryMinFreeMb`). The reading comes from `MachineStats.memory`, the same one `machine_stats` uses. Turns started in the last minute count at an agent's usual size (1.5 GB), because a new agent hasn't grown yet. The task stays queued, and its wait reason and log say why ("Waiting for memory on this computer: only 2.5 GB of 16 GB memory free…"). The server checks again every 15 seconds, and whenever a turn ends. The memory guard holds a turn back only while another turn here holds a slot. Memory that no Box Yard turn holds won't free up by waiting, so one turn always runs. Load isn't part of this guard.

Captains, the Coordinator and side threads run outside this cap. On boxes, pods and containers, a `same` sub-task still runs in its parent's slot.

## Harness, model and effort

A sub-task runs on its parent's agent (harness), model and effort unless its `spawn_subtasks` item names its own `agent`, `model` or `effort`. They are stored as the sub-task's own pins, like a `create_task` model/effort pin: every later turn uses them, and `get_task`, the task header and `turn.json` show them. A parent with no model or effort pin of its own passes none on, so its sub-tasks follow the routing chain each turn as it does. A sub-task on another harness than its parent's doesn't take the parent's model or effort (they belong to that harness): what it leaves out follows the new harness's defaults and routing, as `continue_task` does.

The server checks each item before it creates any (`parseSpawn`, `subtaskPins` in `server/subtasks.ts`) and refuses the whole call with the item's number on a bad value: an unknown agent or effort, a model name with spaces, a model another harness owns (a Cursor pin must be a Cursor-only id or one in Cursor's catalog), Ultra effort off Codex, or any effort on Cursor (its ids carry the effort) or OpenCode (provider/model#variant). A different harness is checked against the runner it would run on, `same` included. None of this changes the environment type rule above.

## Existing stores

The append-only migration adds the nullable type column and a trigger preventing changes once populated. It deliberately does not backfill from requested runners, project defaults or worker files. On first use, an existing lineage is checked through its parent links, project, root and depth. The root's first recorded turn must have an authoritative placement and provider record (stable own-runner IDs can use their server provider routing). A fresh task with no prior turn can use its current server placement. Verified descendants are then pinned.

Missing original turn placement/provider records, missing ancestors, cross-project links, cycles or conflicting persisted types block descendant creation/placement with a clear error. Ambiguous legacy top-level tasks may continue their own work, but cannot spawn until authoritative original lineage exists; changing a runner or retrying does not erase this restriction. Starting a new top-level task intentionally selects a new origin. This conservative compatibility behavior can leave old trees waiting for review.

This boundary governs server-orchestrated task placement. It does not undo past execution, harden containers, restrict a task's network/process capabilities inside its environment, or authorize an agent to control manager tools. Mock mode's folder providers simulate runner types for development and tests; they provide no physical isolation. Regression fixtures use inert provider routing and do not execute live agents or contact providers.
