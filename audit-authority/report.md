# Offline authority-boundary coverage review

Reviewed public PR [#18](https://github.com/AgentSystemLabs/box-yard/pull/18), `contain-task-runner-and-archive-boundaries`, at **ed152eaf5271ba84782003afe753a94ea1f4e24c**. GitHub reported OPEN at this review. This is scope 4: delivery, manager turns, MCP dispatch and regression design. No production code changed, no PR/merge, no live agents, services, Docker, SSH, credentials or installations were used.

**Result:** the runner-ceiling fixes do not close message-origin authority routes. Existing-host delivery, manager mediation, mixed-turn picks and hook-created roots need separate enforcement. This agrees with the unresolved relay risk already recorded in `docs/security/runner-remediation.md:129`. The observations below establish routing and fake privileged effects; they do not establish that any real model obeyed a malicious instruction or that a host command executed.

## High findings and preconditions

**H1 — an isolated task can submit executable-turn input to an existing host task, without changing either runner.** `TaskManager.apply` dispatches `message_agent` at `server/tasks.ts:7233` and `message_parent` at `server/tasks.ts:7267`. `deliverAgentMessage` resolves a target globally by ID or case-insensitive title at `server/tasks.ts:8084`; the only project-boundary check there compares status-only visibility (`8094`). It queues raw worker content with an agent source (`8110`) and can change an idle target to queued (`8120`). There is no sender/target runner-ceiling or sandbox-capability check. The sender label is correct but is not authorization. A direct or nested isolated task can therefore reach an already-local/SSH parent or unrelated task, including another project when visibility settings agree. Preconditions: target exists, source can name/find it, rate limit not exceeded, target is eligible to resume, and its model acts on the text. The deterministic part is delivery/wake; command execution remains model-dependent. A host-runner override is unnecessary.

**H2 — manager-only tools do not carry the originating task's authority.** The Captain route uses server-selected task/project metadata (`server/tasks.ts:8155`, `server/captains.ts:758`), so forged event `source`, `taskId`, approval text or sender headers do not directly spoof the stored principal. However, `Captain.turn` concatenates worker bodies into an ordinary turn (`server/captains.ts:1019`). MCP authentication reconstructs only role/project/readOnly (`server/mcp.ts:118`, `3566`), and labels outgoing task input as Captain/Coordinator (`424`, `1566`). An existing local/SSH task accepts `send_to_task` without a runner override; a host-default project accepts new root tasks because `requireNewRunner` permits its configured host runner (`444-448`, `1330`). A malicious model-selected request can therefore cross the boundary through a legitimate manager. Preconditions: manager sees worker/repository/tool output and follows the requested privileged action, and a host-authorized target/project is accessible to that role. Captain project scoping works, but it does not restrict the origin of an action inside that project. Shell-free managers still have privileged MCP effects.

**H3 — a real human pick becomes an ambient turn-wide host grant.** `shared/runTargets.ts:279-283` drops messages with no pick before checking agreement. A human message with `@local` plus an unpicked worker message yields a local pick. Captain turns aggregate all answering metadata (`server/captains.ts:1053`); Coordinator turns similarly activate the human pick while also including task notices (`server/orchestrator.ts:747`, `759`). `humanHostPick` checks configured authentication and a matching runner, not a particular human message/action/target (`server/mcp.ts:439-441`). `send_to_task` elevates the model-selected task using that ambient pick (`1560`), then sends arbitrary model text. Preconditions: auth configured, an actual human whole-message host pick active in the turn, and the manager selects a different target/action influenced by untrusted content. No textual fake approval is needed. The real turn methods under both supported manager CLIs exposed this effect to the scripted fake callback. Mixing is not the only persistence issue: an earlier malicious session turn may influence a later human turn.

**H4 — automation can create a new host-authorized root from isolated worker output.** Hooks render worker-controlled summary/title values (`shared/hooks.ts:189-211`, `server/hooks.ts:281`). `HookEngine.fire` forwards manager messages with source `hook` (`345`, `372`, `377`), or calls `tasks.createTask` without `subtask`, `runsOn` or originating authority (`384`). `TaskManager.createTasks` then grants the new root the current project runner ceiling (`server/tasks.ts:1266-1268`). A pinned isolated task can remain in a project whose default becomes local/SSH, while a matching enabled create-task hook starts a new host task with its rendered output. Preconditions: such an isolated task and host-default project, an enabled matching hook/event and its guards allowing a fire. The fixture ran the real extracted hook fire and real extracted task creation against in-memory state: **the new root received `runner_ceiling = local`**. No manager-model cooperation was involved in assigning that authority. Any subsequent malicious execution still depends on the host task's behavior. A general automation-approval setting does not bind the worker's substituted content to a safe host action.

## Additional routes to preserve in regression coverage

Manager-to-manager relay loses lineage: `CaptainManager.coordinatorMeta` copies the Coordinator's current picks (`server/captains.ts:348-354`). `app.ts:807` wires those picks; Captain replies/reports become notices containing project/captain/replyTo/FYI metadata (`server/app.ts:808-815`), without worker-origin authority. Coordinator notices are read on automatic and human turns (`server/orchestrator.ts:689`, `713`, `747`). Captain replies delivered through a waiting MCP tool result also need the same constraints (`server/captains.ts:1093`). A Captain → Coordinator → another Captain route must not cleanse the originating constraint.

FYI is a scheduling property. Direct task FYIs persist in task messages but do not queue (`server/tasks.ts:8109-8114`); Captain FYIs persist as user-role messages and return without pending (`server/captains.ts:769-773`). Captain turn SQL excludes agent FYIs (`server/store.ts:2912-2918`). These protections should remain. They do not authorize later operations when the content reappears through transcript/history tools, a report, a summary or a recap. Coordinator FYIs explicitly join later updates (`server/orchestrator.ts:689-693`). A question/wait overrides FYI by design; changing that flag must not change the sender's authority.

Restart/retry retains content: `Captain.resume` rewinds its open-turn watermark and retries unanswered messages (`server/captains.ts:998-1011`); the next turn currently runs with the same unrestricted role tools. Compaction, recap, archive restore, continuation on another harness and durable delivery uncertainty must preserve authorization lineage rather than infer trust from a new role label or session.

## Server-enforced design for the parent implementation

1. Keep **execution authority and provenance in server state**, separate from `source` display strings, task runner settings and model text. Record source task/turn, actual boundary/destination, allowed targets/effects and approval lineage. Worker event IDs or tool arguments cannot choose that principal. Inherit restrictions through descendants, root tasks spawned by hooks, schedules, manager replies/tool results, queue edits, reports, summaries and recaps. The existing runner ceiling remains a useful placement guard but is too coarse as message authority.
2. Gate effects at both real task delivery and MCP handlers, then recheck physical placement at assignment/launch. Compute allowed effects from the originating capability and target capability; an unchanged local/SSH target still needs authorization. Cover create/batch/send/reply/steer/queued-edit/reopen/continue plus hooks/schedules/settings/machines/connector actions that can route or execute work. Reject atomically before task creation, queueing, ceiling mutation or provider calls. Denying an explicit runner override alone leaves existing targets and indirect automation open.
3. Remove **ambient human pick → arbitrary task elevation**. Treat picks as routing hints. Host authorization should be an authenticated server-created grant bound to an exact target (or bounded creation specification), destination, operation and final prompt/attachments digest, with expiry and replay/idempotency handling. Present the concrete final action to the human when it exceeds existing authority. Authentication being enabled is not an action grant. Approval text generated by a model or forwarded by another manager cannot mint/rebind it.
4. Use restricted manager sessions for worker/repository/tool-derived content and approved server operations for broader effects. A per-turn “highest-ranked sender” or “human present” flag is unsafe, and resetting a flag at turn end cannot erase instructions retained in the CLI session. Either keep durable least-authority context across session/resume/compaction, or isolate privileged approval execution in a component that never interprets the untrusted prose. Propagate lineage on Captain/Coordinator handoffs; replacing it with `source:coordinator` must not confer authority.
5. Preserve useful reporting through an attributed data/review channel. Same-sandbox collaborations remain possible within explicitly allowed boundary/target scopes. A rejected cross-boundary request can be shown to the human for a concrete approval; the manager's decision to paraphrase or mark it FYI is not that approval. Hook templates and approved schedules need bounded actions and restricted substitutions, rather than blanket execution authority for arbitrary future summaries.

The compatibility cost is real: automatic cross-sandbox task messaging and manager-initiated host work must become constrained operations or require a concrete authorized grant. Merely blocking all `message_captain`/`message_agent` would break benign delegation and still leave repository/tool-output, hooks and persistent manager context. None of these tests establishes an absolute no-escape guarantee; runtime/kernel/network boundaries and host-authorized task behavior require separate review.
